# 数据中台治理图学习项目

`src/data_platform` 是一个使用本地 Mock 数据任务、MongoDB 持久化检查点的
LangGraph 学习示例，按照 `graph_optimize_codex.md` 的建议把数据治理流程拆成
可审计的状态机。项目额外以内存 Mock MQTT Broker、WebSocket 和事件回放演示
“通知、查询状态、持续交流”这一常见异步任务交互模式；不需要真实 MQTT 服务。

## 启动

先复制 `.env.example` 为 `.env`，并将 `MONGODB_URI` 替换为已授权的实际连接串；
不要将密码提交到 Git。数据中台流程会在 `potato_data_platform` 数据库的
`langgraph_checkpoints` 和 `langgraph_checkpoint_writes` 集合中保存检查点。

然后在项目根目录执行：

```powershell
pip install -e .
python -m data_platform
```

然后打开 <http://127.0.0.1:8003>。

也可以直接执行：

```powershell
uvicorn data_platform.api:app --host 127.0.0.1 --port 8003
```

## 如何学习这条链路

1. 输入治理请求并启动，图会在 `review_plan` 的 `interrupt` 暂停。
2. 浏览器保存返回的 `run_id`，订阅 `governance/runs/{run_id}/#` Mock MQTT 主题，
   再连接运行 WebSocket；首次连接会回放创建时已经发生的事件。
3. 点击“批准计划并继续”，后端用同一个 `thread_id` 发送 `Command(resume=...)`，从检查点恢复。
4. `execute_next` 通过幂等键创建 Mock 外部任务，`wait_external` 再次中断等待回调；
   后台协程会自动上报 25%、50%、75%、100% 的进度，最后走正常回调恢复图。
5. 每次关键状态变化都会先发送 Mock MQTT 通知。前端收到通知后调用
   `GET /api/runs/{run_id}` 获取事实快照，随后由运行 WebSocket 持续打印详细事件。
6. 仍可点击成功/失败按钮抢先模拟回调，观察运行级锁如何防止自动协程重复恢复同一图。
7. 运行进入终态后点击任务交流入口，发送消息并观察 WebSocket 返回的本地规则回复。

## 实时通信时序

```
前端 POST /api/runs ──> LangGraph interrupt(审核)
       <── run_id + 快照 ── 前端订阅 Mock MQTT、连接运行 WebSocket（回放事件）

后台/人工动作 ──> RunManager 写入事件 ──> Mock MQTT 通知
前端收到通知 ──> GET /api/runs/{run_id}（事实快照）
                    └── WS /ws/runs/{run_id}?after=序号（详细事件、聊天）
```

这里 MQTT 通知故意不携带完整任务状态；它仅说明“应刷新”。完整状态以 REST
快照为准，详细过程以 WebSocket 的单调递增 `sequence` 事件为准。这能避免把可能
重复、乱序或丢失的通知错误地当作业务事实。

### WebSocket 契约

- `WS /ws/mock-mqtt`：先发送
  `{"action":"subscribe","topic":"governance/runs/{run_id}/#"}`；服务端返回
  `mqtt_notification`，其中包括主题、序号、事件类型、运行 ID 和可选任务 ID。
- `WS /ws/runs/{run_id}?after={sequence}`：先返回 `snapshot`，再回放指定序号之后的
  `event`；连接保持期间持续推送新事件。浏览器以 sequence 去重，重连不会重复打印。
- 同一运行 WebSocket 可发送
  `{"type":"chat.send","content":"..."}`。服务端记录用户消息和本地确定性回复，
  但不会调用 LLM 或发布 MQTT 通知。

## 关键设计

- **检查点**：`MongoDBSaver` 以 `configurable.thread_id` 隔离每个治理运行。运行管理器通过确定性规则从 `run_id` 推导 thread_id，因此应用重启后，前端仍能用原 run_id 读取、审核或恢复挂起流程。
- **人工审核**：计划是显式结构化数据，审核拒绝不会启动外部任务；跳过质检等质量门禁也会显示在计划中并等待审核。
- **异步任务**：Mock 平台的 `start_task` 返回 `task_id`；后台协程按 25%、50%、75%、
  100% 自动推进，按钮可抢先成功或失败回调。重复相同幂等键只返回原任务，运行级锁
  防止自动和手动回调重复恢复检查点。
- **实时职责**：`realtime.py` 的事件表保存当前进程内有限事件，用于 WebSocket 重连
  回放；Mock MQTT 只广播轻量变化通知。两者都会在服务停止时清空。
- **事实正确性**：任务失败进入 `FAILED`，不会继续入库；发布成功前不会显示服务地址或治理成功。
- **依赖边界**：没有真实 LLM、MQTT 或数据中台接口；采集、质检、清洗、入库和发布任务均为本地 Mock。唯一外部基础设施是 MongoDB，用于可靠保存 LangGraph 检查点。

## MongoDB 检查点与恢复

服务启动时会创建共享 `MongoClient`、执行 `ping` 并由 `MongoDBSaver` 初始化必要索引；
连接或鉴权失败会让服务在启动阶段失败，防止审核中断无法保存。审核 API 收到决定时：

1. 根据 `run_id` 推导 `thread_{run_id}`；
2. 从 MongoDB 读取该 thread 的最新 checkpoint；
3. 使用相同 config 执行 `Command(resume=...)`；
4. 将恢复后的状态再次写入 MongoDB。

这意味着服务重启不会丢失审核中的图状态。Mock 外部任务本身仍只存在当前进程；它用于
教学按钮演示，不应作为真实任务引擎实现。

## 推荐阅读顺序

先看 `domain.py` 的枚举和请求模型，再看 `graph.py` 的节点与边；接着阅读
`realtime.py` 中的 Mock MQTT 与事件回放实现，最后看 `manager.py` 如何把 HTTP
动作映射为检查点恢复和实时事件。前端 `static/app.js` 展示 REST 快照、MQTT 通知
桥与运行 WebSocket 的协作方式。
